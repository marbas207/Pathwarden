# PW-028: Possible management plane: review whether it manages Tier Zero

**Category:** Hygiene
**Typical owner:** AD / identity team, with the infrastructure teams that run SCCM, SCOM, backup and virtualization

## What this finding means
Something in the directory looks like part of a management system (SCCM,
SCOM, WSUS, backup, virtualization or Entra Connect), but the directory
doesn't show whether it manages Tier Zero. Pathwarden doesn't treat it as
Tier Zero; it asks you to check. There are three levels:

- **Inferred (medium):** structure the product creates.
  - Full Control of `CN=System Management,CN=System` is granted to SCCM
    site servers, so the holder is very likely one.
  - A `MSOMSdkSvc/` service principal name belongs to a SCOM management
    server or its Data Access account, and `MSOMHSvc/` (the Health Service)
    on a computer that isn't a domain controller or CA server to a SCOM
    management server or gateway (one finding per domain lists those
    computers); `SCVMM/` belongs to Virtual Machine Manager.
  - The Hyper-V live migration and console service principal names
    (`Microsoft Virtual System Migration Service/`, `Microsoft Virtual
    Console Service/`) mark Hyper-V hosts. One finding per domain lists
    them, and notes the failover cluster nodes.
  - A computer that can read the password of the Entra Connect sync service
    account (`ADSyncMSA...`), or a group named `ADSyncAdmins`, when no sync
    account in the domain can DCSync.
- **Inferred, Tier Zero computers (high):**
  - A domain controller or CA server is an SCCM client (it has the
    `CmRcService/` service principal name of SCCM Remote Control, or a GPO
    that applies to it pushes the SCCM client), and its forest has several
    site servers, or none in the collection. With the built-in collector,
    SCCM's site objects narrow several site servers to the one of the
    client's site first; the finding says whether they were read.
  - A GPO that applies to a domain controller or CA server points it at a
    WSUS server that isn't a computer in the collection (an IP address, a
    DNS alias, or a server in another forest). Built-in collector only.
  - A domain controller or CA server is a SCOM agent (it has the
    `MSOMHSvc/` service principal name) and no AD integration group names
    its management server.
  - From its Tier Zero settings file (the management agents the script
    reads on the computer): an SCCM client whose site code is ambiguous (two
    site objects publish it), a SCOM agent or a Hyper-V virtual machine
    whose server or host the registry names but which doesn't match a single
    computer in the collection (Pathwarden never guesses from a short
    name in another domain), and a backup agent (Veeam, Commvault,
    NetBackup, DPM), whose backup server the computer doesn't name. A later
    run without a current, trusted file from the computer holds these as can't
    tell.
  - A SCOM AD integration group lists domain controllers or CA servers as
    agents, but its management server isn't in the collection.
- **Heuristic (low):** names only (`SVC_VEEAM`, `WSUS01`, `ESX01`, an
  `MSOL_` account without replication rights). One finding per product and
  domain lists them all. The `ESX Admins` group is PW-029.

With a single site server in its forest (or of its site), an SCCM client
domain controller makes that server Tier Zero instead (PW-025), and so does
a WSUS server that is a computer in the collection.

## Why attackers care
Whoever controls a management system controls what it manages:
- an SCCM site server or Full Administrator can deploy code as SYSTEM to
  every client;
- a SCOM management server or administrator can run tasks on every agent;
- a WSUS server (or anyone on the path to an HTTP one) can push updates;
- a backup server holds copies of the domain controllers, and with them every
  password hash;
- a hypervisor administrator controls every virtual domain controller's disk
  and console. ESXi hosts joined to AD grant administrator rights to any
  group named "ESX Admins" by default.

When domain controllers or CA servers are among the managed computers, the
management system is part of Tier Zero whether or not anyone decided so.

## Before you change anything
Check what the system manages. Directory data can't show it; the computers can:

| Product | On a domain controller, look for |
|---|---|
| SCCM client | `HKLM\SOFTWARE\Microsoft\CCM`; `HKLM\SOFTWARE\Microsoft\SMS\Mobile Client` value `AssignedSiteCode` |
| SCOM agent | `HKLM\SOFTWARE\Microsoft\Microsoft Operations Manager\3.0\Agent Management Groups` |
| WSUS | `HKLM\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate` value `WUServer` |
| Hyper-V guest | `HKLM\SOFTWARE\Microsoft\Virtual Machine\Guest\Parameters` value `HostName` |
| VMware guest | `HKLM\SOFTWARE\VMware, Inc.\VMware Tools` |
| Backup agents | services from Veeam, Commvault, NetBackup, Rubrik, Cohesity, ... |

Also check who administers the system (local Administrators, the product's
own roles): those accounts become Tier Zero if the system does.

## Fix
### Option A: It manages Tier Zero: make it Tier Zero, or separate it
1. Either take the Tier Zero computers out of its management (uninstall the
   agent, point them at a Tier Zero instance), or add the system (for
   example CM01.SCALE.LOCAL) under Additional Tier Zero in Settings.
2. If it becomes Tier Zero, Pathwarden reports who controls it (PW-003).
   Fix those, and restrict the product's own administrators to Tier Zero
   admins.
### Option B: It doesn't manage Tier Zero
Accept the finding as a risk in Settings, with the reason, so the review is
recorded (for example "CM01 manages workstations only; DCs are not SCCM
clients, checked 2026-10-10"). Set a review date: what a system manages
changes.

### PowerShell
```powershell
# On each domain controller: management agents (read-only)
$keys = 'HKLM:\SOFTWARE\Microsoft\CCM',
        'HKLM:\SOFTWARE\Microsoft\SMS\Mobile Client',
        'HKLM:\SOFTWARE\Microsoft\Microsoft Operations Manager\3.0\Agent Management Groups',
        'HKLM:\SOFTWARE\Policies\Microsoft\Windows\WindowsUpdate',
        'HKLM:\SOFTWARE\Microsoft\Virtual Machine\Guest\Parameters',
        'HKLM:\SOFTWARE\VMware, Inc.\VMware Tools'
foreach ($dc in (Get-ADDomainController -Filter *).HostName) {
    Invoke-Command -ComputerName $dc -ScriptBlock {
        param($keys) foreach ($k in $keys) { if (Test-Path $k) { [pscustomobject]@{ Key = $k; Values = (Get-ItemProperty $k | Out-String).Trim() } } }
    } -ArgumentList (,$keys)
}

# SCCM site servers: who has Full Control of System Management
$sm = "AD:\CN=System Management,CN=System," + (Get-ADDomain).DistinguishedName
(Get-Acl $sm).Access | Where-Object ActiveDirectoryRights -eq 'GenericAll' |
    Select-Object IdentityReference, IsInherited
```

## Verify
Collect again. With Option A the system is listed as "Configured as Tier
Zero" and the finding is gone; with Option B the finding shows as an
accepted risk.

## Rollback
Remove the object from Additional Tier Zero in Settings, or remove the
accepted risk.
