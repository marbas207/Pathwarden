# PW-006: Kerberoastable account with Tier Zero access

**Category:** Attack path
**Typical owner:** AD / identity team with the service owner

## What this finding means
A user account with a service principal name (SPN) is in Tier Zero or has a path
to it. Any domain user can request a Kerberos service ticket for it, and that
ticket is encrypted with a key derived from the account's password.

Group and standalone managed service accounts (gMSA, sMSA) are not reported:
the domain gives them a 240-byte (120-character) random password and rotates
it, so their tickets can't be cracked. In SharpHound collections Pathwarden
recognizes them from the `gmsa` and `msa` flags; in RustHound-CE and built-in
collections, which have no such flag, from the computer-account bit
(userAccountControl 0x1000) on a user object. In those collections a user
account an administrator gave the computer-account bit by hand, which still
has a human-set password, is treated as managed and not reported: check SPN
accounts with that bit
(`Get-ADUser -LDAPFilter "(userAccountControl:1.2.840.113556.1.4.803:=4096)"`)
if you collect with RustHound-CE or the built-in collector.

## Why attackers care
Kerberoasting (Steal or Forge Kerberos Tickets: Kerberoasting, T1558.003) needs only
a normal domain account: request tickets for every SPN, take them offline and crack
the passwords. Service account passwords are often old, human-chosen and never
rotated, and RC4 tickets crack quickly. A cracked privileged service account means
domain compromise without any alert on the target.

## Before you change anything
- Identify the service using the SPN (`setspn -L <Account>`), the computers running it,
  and who owns it.
- Check whether the SPN is still used: event 4769 on domain controllers shows
  service ticket requests for the account. No requests over weeks often means a
  stale SPN.
- If the account is privileged only because of a group it does not need (common
  for old SQL service accounts in Domain Admins), removing that membership is part
  of the fix.

## Fix
### Option A: Move the service to a group Managed Service Account (recommended)
1. Create a gMSA (`New-ADServiceAccount`) allowed for the service's computers.
2. Install it on the computers (`Install-ADServiceAccount`) and change the service to
   run as `<Domain>\<gMSA>$` with an empty password.
3. Move the SPNs to the gMSA, then disable the old account.
gMSA passwords are 240-byte (120-character) random values rotated automatically: not crackable.
### Option B: Remove unneeded SPNs or privileges
Remove stale SPNs with `setspn -D`, and remove the account from privileged groups it
does not need.
### Option C: If the account must stay
Set a random password of 25+ characters, enable AES-only Kerberos for the account
("This account supports Kerberos AES 128/256 bit encryption" in ADUC **Account**
tab), then change the password once more so the account has AES keys: a
password set before the domain supported AES has none, and with AES only the
service stops working. Rotate the password on a schedule after that.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Kerberoastable user accounts
Get-ADUser -Filter { ServicePrincipalName -like "*" } -Properties ServicePrincipalName, PasswordLastSet, MemberOf

# Option A: create a gMSA (needs a KDS root key in the forest)
New-ADServiceAccount -Name "<gMSA>" -DNSHostName "<gMSA>.<Domain>" `
    -PrincipalsAllowedToRetrieveManagedPassword "<ServerGroup>"
Install-ADServiceAccount -Identity "<gMSA>"     # run on each service computer

# Option B: remove a stale SPN
setspn -D <SPN> <Account>

# Option C: AES only (0x18 = AES128 + AES256), then reset the password
Set-ADUser -Identity "<Account>" -Replace @{ 'msDS-SupportedEncryptionTypes' = 24 }
Set-ADAccountPassword -Identity "<Account>" -Reset -NewPassword (Read-Host -AsSecureString "New password")
```

## Verify
`Get-ADUser "<Account>" -Properties ServicePrincipalName` shows no SPNs (Options A/B),
or `msDS-SupportedEncryptionTypes` is 24 and PasswordLastSet is recent (Option C).
Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
Re-register an SPN with `setspn -S <SPN> <Account>`; switch the service back to the
old account in the Services console. Keep the old account disabled, not deleted,
until the gMSA has run cleanly for a while.
