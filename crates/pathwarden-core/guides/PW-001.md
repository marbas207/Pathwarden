# PW-001: Broad group has a path to Tier Zero

**Category:** Attack path
**Typical owner:** AD / identity team

## What this finding means
A group that contains almost every account (Domain Users, Domain Computers,
Authenticated Users, Everyone, or the builtin Users group) can reach a Tier Zero
object such as Domain Admins, a domain controller or the domain itself. Because
every account is a member, any single compromised user or workstation is enough
to take over the domain.

## Why attackers care
After phishing one user, an attacker runs BloodHound and looks for this:
a right or nesting granted to a broad group that leads to domain control. They
need no privilege escalation exploit, only the permission already
granted (for example GenericAll on a privileged group, or Domain Users nested in a
local Administrators group on a server where admins log on). Typical follow-ups
are account manipulation (T1098) and credential theft from a privileged session.

## Before you change anything
- Read the attack path in the finding: the fix is usually the *first* step that
  is not plain membership (the permission or nesting granted to the broad group).
- Find out why it was granted. Search change tickets, and check who uses it:
  for a group nesting, `Get-ADGroup <Group> -Properties whenChanged, info, description`.
- For ACL grants, enable auditing of the target object (Directory Service Changes,
  event 5136) for a short period if you are unsure whether anything relies on it.
- The report's Remediation path tab lists the smallest set of changes that
  closes every path, which often fixes this finding together with others.

## Fix
### Option A: Remove the right or nesting granted to the broad group (recommended)
1. Identify the first non-membership step of the path in the finding (for
   example `DOMAIN USERS -[GenericAll]-> HELPDESK`).
2. For an ACL: open **Active Directory Users and Computers**, enable
   **View > Advanced Features**, open the target object's **Properties > Security >
   Advanced**, and remove every write entry of the broad group the finding names
   (the path stays open while one is left). Keep its read entries. If an
   entry is inherited, remove it on the parent container shown in the finding,
   then check inheritance on the objects below it.
   On a GPO, use GPMC > the GPO > **Delegation > Advanced** instead: Authenticated
   Users and Domain Computers need Read (and Apply group policy where Security
   Filtering uses it) for the GPO to apply. For the GPO's SYSVOL folder, see PW-027.
3. For a nesting (for example Domain Users in a privileged group): open the
   privileged group's **Properties > Members**, select the broad group, **Remove**.
4. For local group membership on a server (AdminTo/CanRDP): remove the broad group
   from the local group, or from the GPO (Restricted Groups / Group Policy
   Preferences) that adds it.
### Option B: Replace with a dedicated group for each tier
1. Create a group for the people who need the access.
2. Grant that group the right, then remove the broad group as in Option A.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Nesting: remove a broad group from a privileged group
Remove-ADGroupMember -Identity "<PrivilegedGroup>" -Members "Domain Users" -Confirm:$false

# ACL: list ACEs granted to a broad group on an object
$dn  = (Get-ADObject -Identity "<TargetDN>").DistinguishedName
$acl = Get-Acl -Path "AD:\$dn"
$acl.Access | Where-Object { $_.IdentityReference -match "Domain Users|Authenticated Users|Everyone" }

# ACL: remove the explicit (non-inherited) ACEs that grant the rights the finding
# names, and save. Add any other right it names to the pattern; leave read entries
# and default extended rights (Change Password, Apply Group Policy) in place
$acl.Access | Where-Object {
    $_.IdentityReference -match "Domain Users|Authenticated Users|Everyone" -and -not $_.IsInherited -and
    $_.ActiveDirectoryRights -match "GenericAll|GenericWrite|WriteDacl|WriteOwner"
} | ForEach-Object { [void]$acl.RemoveAccessRule($_) }
Set-Acl -Path "AD:\$dn" -AclObject $acl
```

## Verify
```powershell
(Get-Acl -Path "AD:\<TargetDN>").Access |
    Where-Object { $_.IdentityReference -match "Domain Users|Authenticated Users|Everyone" }
Get-ADGroupMember "<PrivilegedGroup>" | Select-Object Name
```
Both should return nothing for the broad group. Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
Re-add the removed ACE or membership (you can re-apply Get-Acl output saved before
the change with `Set-Acl`). Save `(Get-Acl "AD:\<TargetDN>").Sddl` to a file before
editing so you can restore the original security descriptor.
