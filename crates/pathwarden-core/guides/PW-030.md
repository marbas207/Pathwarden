# PW-030: Object outside Tier Zero controls a Tier Zero object through another system

**Category:** Attack path
**Typical owner:** the team that runs the system the collector describes (server team for scheduled tasks and services, database team for SQL Server)

## What this finding means
A specialist collector (TaskHound, MSSQLHound, ...) reported a relationship
outside Active Directory that gives an object outside Tier Zero control of a
Tier Zero object. For example: a scheduled task on a member server stores the
password of a Domain Admin, so every administrator of that server can recover
the password and act as the Domain Admin.

The finding names the source in its title. Pathwarden only follows such a
relationship when a reviewed mapping pack says it gives control; the file
itself can't. The evidence rests on the collector's data, not on the
directory, so confirm it on the system it describes.

## Why attackers care
Tier Zero is only as safe as everything that holds a way into it. Stored
credentials (T1555, Credentials from Password Stores; T1003.004, LSA Secrets),
database logins that run code as a service account, and management systems
that push code to domain controllers are all ways around AD permissions that
directory-only tools never see. Attackers look for them because they are rarely
reviewed.

## Before you change anything
- Read the step in the finding's path that comes from the source, and confirm
  it on the system: open the scheduled task or service, the SQL Server login,
  or whatever the source describes.
- Find out who depends on it. A scheduled task that runs as a Domain Admin
  usually does something that needs far less: find what, and with which
  account it could run instead.
- Note the current configuration (export the task, script the login) so you
  can roll back.

## Fix
### Option A: Remove the relationship at its source (recommended)
Follow the fix text in the finding: it comes from the source's mapping pack.
Typical fixes:

| Source | Relationship | Fix |
|---|---|---|
| TaskHound | Scheduled task stores a password | Run the task as a gMSA, or as SYSTEM if it needs no network identity; then rotate the account's password |
| TaskHound | Service runs as a domain account | Run it as a gMSA or a virtual account; then rotate the account's password |

When a credential was stored on a computer outside Tier Zero, **rotate the
account's password after the fix**: any administrator of that computer could
already have read it.

### Option B: Bring the system into Tier Zero
If the system administers Tier Zero (a backup server, a management
server), add it under Additional Tier Zero in Settings and manage it like Tier
Zero: dedicated admins, Tier Zero logon restrictions, and the hardening of a
domain controller. You can name external objects there by their ID.

### PowerShell
```powershell
# Scheduled tasks that store a password, on one computer
Get-ScheduledTask -CimSession "<Computer>" |
    Where-Object { $_.Principal.LogonType -eq 'Password' } |
    Select-Object TaskPath, TaskName, @{n='RunAs';e={$_.Principal.UserId}}

# Run a task as a gMSA instead (the gMSA must be allowed on the computer)
$p = New-ScheduledTaskPrincipal -UserId "<Domain>\<gMSA>$" -LogonType Password
Set-ScheduledTask -CimSession "<Computer>" -TaskPath "<TaskPath>" -TaskName "<TaskName>" -Principal $p

# Services that run as a domain account
Get-CimInstance Win32_Service -ComputerName "<Computer>" |
    Where-Object { $_.StartName -like '<Domain>\*' } | Select-Object Name, StartName

# Rotate the exposed account's password
Set-ADAccountPassword -Identity "<Account>" -Reset -NewPassword (Read-Host -AsSecureString "New password")
```

## Verify
Collect again with the same source **and its coverage file**
(see `docs/opengraph.md`) that lists the computer or instance you changed,
and analyze the new collection. Pathwarden marks the finding fixed only when the source covered that computer this run;
without a coverage file it stays open as "can't tell".

## Rollback
Re-import the exported task (`Register-ScheduledTask -Xml (Get-Content task.xml -Raw)`),
or restore the service account with `sc.exe config <Service> obj= <Account>`.
Do not restore a password that was exposed: set a new one.
