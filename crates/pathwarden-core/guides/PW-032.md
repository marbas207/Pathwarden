# PW-032: Entra ID controls on-premises Tier Zero (hybrid path)

**Category:** Attack path
**Typical owner:** the Active Directory team together with the Entra ID (or Intune) team

## What this finding means
A path starts in Entra ID and ends in on-premises Tier Zero. A cloud role, or
whoever compromises one of its holders, can take over an Active Directory
object that is Tier Zero or has a path to it. Pathwarden reports two
crossings today:

- **Password writeback** (`SyncedToADUser`). The AD account is synchronized
  to Entra ID, and the Entra Connect connector account can reset its password
  on-premises. A helpdesk, user or authentication administrator who resets
  the Entra copy's password sets the AD password too. Pathwarden draws this
  only when the AD data shows the connector account's reset permission on
  that account. It can't see whether writeback is turned on, so confirm that
  in the Entra Connect configuration.
- **Intune on a hybrid-joined computer** (`SyncedToADComputer`). The AD
  computer is hybrid joined and Intune-managed, so an Intune administrator
  can run a script on it as SYSTEM. That takes over the computer, and with
  it the Tier Zero logons on it.

If the AD object is not Tier Zero itself but has a path to it, the finding
says so and its severity starts at medium.

## Why attackers care
Cloud administrators are easier to phish than domain admins, and helpdesk
roles are widely granted. A path from a cloud role down to a domain admin
crosses a boundary that most organizations treat as separate: the cloud team
owns one half and the AD team the other (T1098, Account Manipulation;
T1072, Software Deployment Tools).

## Before you change anything
- Confirm the crossing:
  - password writeback in Entra Connect (**Optional features > Password
    writeback**);
  - the device's join type and management in Intune (**Devices > Windows**).
- Check whether the account or computer needs to be in sync scope or in
  Intune at all. Tier Zero accounts and servers rarely do.

## Fix
### Option A: Take Tier Zero out of the cloud's reach (recommended)
- **Synchronized Tier Zero accounts:** exclude them from Entra Connect sync
  (an OU or attribute filter). Tier Zero administrators use separate,
  cloud-only accounts in Entra ID and AD-only accounts on-premises.
- **Writeback permission:** remove the Entra Connect connector account's
  *Reset password* permission from Tier Zero OUs and accounts. Accounts
  protected by AdminSDHolder (`adminCount=1`) don't have it by default, so
  someone granted it on purpose.
- **Intune on Tier Zero computers:** don't enroll Tier Zero servers, or
  workstations Tier Zero accounts log on to, in Intune. Otherwise scope
  Intune administrators to them with Intune RBAC and scope tags.

### Option B: Reduce the cloud side
Remove holders of the role in the path who don't need it, and protect those
who stay with role-assignable groups and Privileged Identity Management.

### PowerShell
```powershell
# Connector account permissions on a Tier Zero account (Entra Connect module, on the Connect server)
Import-Module "C:\Program Files\Microsoft Azure Active Directory Connect\AdSyncConfig\AdSyncConfig.psm1"
Get-ADSyncObjectsWithInheritanceDisabled -SearchBase "<Tier Zero OU DN>"
(Get-Acl "AD:\<Tier Zero account DN>").Access |
    Where-Object { $_.IdentityReference -like '*MSOL_*' } |
    Select-Object IdentityReference, ActiveDirectoryRights, ObjectType

# Remove an explicit reset-password grant for the connector account
$acl = Get-Acl "AD:\<DN>"
$acl.Access | Where-Object { $_.IdentityReference -like '*MSOL_*' -and -not $_.IsInherited } |
    ForEach-Object { [void]$acl.RemoveAccessRule($_) }
Set-Acl "AD:\<DN>" $acl
```

## Verify
Collect AD data and AzureHound data again and analyze them. The
finding is marked fixed only when that tenant was collected this run;
otherwise it stays open as "can't tell".

## Rollback
Re-add the account to sync scope (and run a sync cycle with
`Start-ADSyncSyncCycle -PolicyType Delta`), re-grant the permission you
removed, or re-enroll the device.
