# PW-023: Account or group outside Tier Zero can log on to domain controllers

**Category:** Hygiene
**Typical owner:** AD / identity team

## What this finding means
A user, computer or group outside Tier Zero can open a session on domain
controllers through Remote Desktop, PowerShell remoting (WinRM) or DCOM. On a
domain controller these rights do not come from a local group, because DCs have
no local accounts database. They come from the domain's built-in groups:
**Remote Desktop Users** (S-1-5-32-555), **Remote Management Users**
(S-1-5-32-580) and **Distributed COM Users** (S-1-5-32-562). These groups are
shared by every DC in the domain. A GPO linked to the Domain Controllers OU can
also grant them.

Pathwarden does not draw this as an attack path: a session alone is not control
of the domain. It is one step from it, though.

## Why attackers care
A logon on a DC puts an attacker's code on the most sensitive server in the
domain. One local privilege escalation (an unpatched driver, a misconfigured
service, a token impersonation bug) turns it into SYSTEM on the DC, which means
the NTDS.dit database, every password hash and the krbtgt key (OS Credential
Dumping: NTDS, T1003.003). It also lets the attacker read whatever the DC
exposes to logged-on users: scripts, shares and memory left by other sessions.

## Before you change anything
- Find out who uses the access and why. Helpdesk and monitoring teams are
  often given RDP to DCs "temporarily", and some monitoring agents use WinRM.
- Monitoring and management tools that need WinRM on DCs should use a
  dedicated, tightly scoped account, ideally in Tier Zero and managed as such,
  or a pull model that needs no inbound logon.
- Check whether the right comes from group membership (most common) or from a
  GPO user right on the Domain Controllers OU; the finding's fix lists both.

## Fix
### Option A: Empty the built-in groups (recommended)
1. In **Active Directory Users and Computers**, open the **Builtin** container
   of the domain.
2. Open **Remote Desktop Users**, **Remote Management Users** and
   **Distributed COM Users**, and remove the account or group from the finding (and
   anything else that is not Tier Zero).
3. Leave Domain Admins and other Tier Zero administrators as they are: they
   can already log on to DCs through Administrators.
### Option B: Remove GPO-granted logon rights
1. In **Group Policy Management**, review every GPO linked to the **Domain
   Controllers** OU (usually only the Default Domain Controllers Policy).
2. Under **Computer Configuration > Policies > Windows Settings > Security
   Settings > Local Policies > User Rights Assignment**, check **Allow log on
   through Remote Desktop Services** and **Access this computer from the
   network**, and remove the account or group from both.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Who is in the built-in remote access groups?
'Remote Desktop Users', 'Remote Management Users', 'Distributed COM Users' |
    ForEach-Object { Get-ADGroupMember -Identity $_ -Recursive | Select-Object @{ n = 'Group'; e = { $_ } }, Name, objectClass }

# Remove the account or group from the finding
Remove-ADGroupMember -Identity 'Remote Desktop Users' -Members '<Account>' -Confirm:$false
```

## Verify
A Remote Desktop or `Enter-PSSession` attempt by the account to a listed DC
must be refused. Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
Add the account or group back with
`Add-ADGroupMember -Identity '<Group>' -Members '<Account>'`, or restore the
user right in the GPO and run `gpupdate /force` on the domain controllers.
