# PW-029: ESX Admins group open to accounts outside Tier Zero (CVE-2024-37085)

**Category:** Hygiene
**Typical owner:** AD / identity team, with the virtualization team

## What this finding means
ESXi hosts joined to Active Directory make every member of a domain group
named **ESX Admins** a full ESXi administrator by default. The host looks the
group up by name, not by SID (CVE-2024-37085). The finding has two forms:

- **The group exists**, and accounts and groups outside Tier Zero are members of it or
  can change it (add members, take ownership, change its permissions).
  - High when the directory shows signs of ESXi or vCenter: a computer whose
    operating system is ESXi or VMware's, or objects named like ESX, vCenter,
    VCSA or vSphere.
  - Low otherwise, for review.
- **The group doesn't exist**, but the directory shows signs of ESXi or
  vCenter (Medium). Anyone who can create a group, or rename a group they
  control, can make a new ESX Admins group and become ESXi administrator.
  Without ESXi evidence, a missing group is not reported.

Pathwarden infers this from the directory only. It can't see whether a host
is joined to the domain, or how its settings are.

## Why attackers care
An ESXi administrator controls every virtual machine on the host: it can
snapshot a virtual domain controller, copy its disk and read `NTDS.dit` with
every password hash, or encrypt all the virtual machines at once. Ransomware
operators have used this path (Microsoft Threat Intelligence, July
2024): create "ESX Admins", add themselves, and take over the hosts.

## Before you change anything
- Ask the virtualization team which ESXi hosts are joined to the domain, and
  which group they grant administration to (the advanced settings
  `Config.HostAgent.plugins.hostsvc.esxAdminsGroup` and
  `Config.HostAgent.plugins.hostsvc.esxAdminsGroupAutoAdd` on each host).
- Check the members of the group. Someone in it may need ESXi access for
  their work; give them that access through a group only Tier Zero admins
  control.

## Fix
### Option A: Turn the automatic grant off (recommended)
1. Update the ESXi hosts. ESXi 8.0 Update 3 turns the automatic grant off by
   default.
2. On older hosts, set `Config.HostAgent.plugins.hostsvc.esxAdminsGroupAutoAdd`
   to `false` (vSphere Client: **Host > Configure > System > Advanced System
   Settings**), and set `esxAdminsGroup` to a group only Tier Zero admins
   control.
3. Remove the ESX Admins permission from each host if it was already granted
   (**Host > Permissions**).
### Option B: Keep the group, locked down
1. Remove the members outside Tier Zero from ESX Admins.
2. Remove the rights others hold on it, so that only Tier Zero admins can
   change it.
3. If the group was missing, create it, empty, with the same protection.
### Option C: No ESXi host uses it
Accept the finding as a risk with the reason, so the review is recorded.

### PowerShell
```powershell
Import-Module ActiveDirectory

# The group, its members and who can change it
$g = Get-ADGroup -Filter "Name -eq 'ESX Admins'" -Properties nTSecurityDescriptor
if ($g) {
    Get-ADGroupMember $g -Recursive | Select-Object Name, ObjectClass
    $g.nTSecurityDescriptor.Access |
        Where-Object { $_.ActiveDirectoryRights -match 'GenericAll|WriteProperty|WriteDacl|WriteOwner' } |
        Select-Object IdentityReference, ActiveDirectoryRights, IsInherited
} else { 'No ESX Admins group' }

# On each ESXi host (PowerCLI): the settings
# Get-VMHost | Get-AdvancedSetting -Name 'Config.HostAgent.plugins.hostsvc.esxAdmins*'
```

## Verify
Collect again (or use Retest on the finding).
The finding is gone when nobody outside Tier Zero is in the group or can
change it, and when the group exists wherever the directory shows ESXi.

## Rollback
Put the members back, or restore the rights on the group. To undo Option A,
set `esxAdminsGroupAutoAdd` back to `true` on the hosts.
