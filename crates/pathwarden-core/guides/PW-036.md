# PW-036: AD CS ESC11: NTLM relay to the CA's RPC interface

**Category:** Attack path
**Typical owner:** PKI / AD CS administrators

## What this finding means
Clients normally request certificates from an Enterprise CA over RPC (the ICPR interface that autoenrollment and certreq use). The CA's `InterfaceFlags` registry value decides whether it insists that those requests are encrypted (packet privacy). On this CA the `IF_ENFORCEENCRYPTICERTREQUEST` flag (0x200) is off, so it also accepts requests over an unencrypted connection authenticated with NTLM, and such a connection can be relayed.

The finding lists the templates that make it exploitable: published by this CA, usable for authentication, and issued without manager approval or extra signatures.

## Why attackers care
This is ESC11, the RPC twin of ESC8. An attacker on the network coerces a domain controller into authenticating to a computer they control (for example with PetitPotam or the printer bug), relays that NTLM authentication to the CA over RPC with tools such as ntlmrelayx or Certipy, and receives a certificate for the domain controller's computer account from one of the listed templates. With it they obtain the DC's credentials and can DCSync the domain. No prior privileges beyond network access are required, which is why this is treated as exposed to every account.

## Before you change anything
- Current Windows Server versions set the flag when the CA is installed, so a CA without it has usually had it removed on purpose, often for old clients. Ask the PKI team why, and check the CA's history (change records, `certutil -getreg CA\InterfaceFlags` on a backup).
- Clients that can't encrypt their requests (Windows XP and Server 2003 era systems, some appliances and non-Windows enrollment tools) will no longer be able to enroll over RPC. Look in the CA's issued certificates for requesters that look like that, and plan for them first.
- Autoenrollment, certreq and the Certificates console on supported Windows versions already encrypt their requests and are unaffected.

## Fix
### Option A: Require encrypted requests (recommended)
1. On the CA server (or remotely with `-config`), set the flag with the certutil command below.
2. Restart Certificate Services; the change takes effect at the restart.
3. Test enrollment from a client (for example `certreq -enroll -machine` or the Certificates console).

### Option B: Block NTLM to the CA server
Disable NTLM for incoming traffic on the CA server (Group Policy: Network security: Restrict NTLM: Incoming NTLM traffic = Deny all accounts), after auditing with the corresponding audit setting. This also blocks the relay, and ESC8 with it.

### PowerShell / certutil
```powershell
# Option A: require encrypted requests on the RPC interface
certutil -config "<CAHost>\<CAName>" -setreg CA\InterfaceFlags +IF_ENFORCEENCRYPTICERTREQUEST
# then, on the CA server
net stop certsvc
net start certsvc
```

## Verify
- `certutil -config "<CAHost>\<CAName>" -getreg CA\InterfaceFlags` lists `IF_ENFORCEENCRYPTICERTREQUEST`.
- Collect again with the built-in collector's Full collection (it reads the flag from the CA's registry as an ordinary domain user) and confirm the finding ID is gone. Pathwarden takes the flag from that collection, or from the CA's Tier Zero settings file (`scripts\Get-PathwardenTierZeroSettings.ps1` run on the CA). Without either, with SharpHound or RustHound-CE data, the report's AD CS data section shows ESC11 as not checked for the CA.

## Rollback
`certutil -config "<CAHost>\<CAName>" -setreg CA\InterfaceFlags -IF_ENFORCEENCRYPTICERTREQUEST`, then restart Certificate Services.
