# PW-004: Tier Zero account logged on to computers outside Tier Zero

**Category:** Attack path
**Typical owner:** AD / identity team together with the admins who own the account

## What this finding means
A Tier Zero account (for example a Domain Admin) had a session on servers or
workstations outside Tier Zero. While logged on, and often afterwards, its
credentials are in that computer's memory, so anyone with admin rights on the computer can
take them.

## Why attackers care
Attackers who gain local admin on any listed computer dump LSASS or steal Kerberos
tickets (OS Credential Dumping: LSASS Memory, T1003.001) and immediately become
Domain Admin. This is one of the most common paths in real intrusions and pentests,
and usually the biggest choke point in the report's Remediation path tab.

## Before you change anything
- Ask the account owner why they log on to those computers (RDP, scheduled task,
  service, mapped drive). Event 4624 on the computer shows logon type: 2/10 interactive
  or RDP, 3 network, 4 batch, 5 service.
- Services or scheduled tasks running as a Tier Zero account must be moved to a
  dedicated, non-privileged service account (or gMSA) first, or they will break.
- Make sure each admin has a separate, non-Tier Zero account for daily work.

## Fix
### Option A: Separate accounts per tier and deny Tier Zero logon elsewhere (recommended)
1. Give the admin a normal account for workstations and a Tier 1 account for
   servers if needed.
2. In **Group Policy Management**, edit a GPO linked to all non-Tier Zero
   computers: **Computer Configuration > Policies > Windows Settings > Security
   Settings > Local Policies > User Rights Assignment**.
3. Add the Tier Zero groups (Domain Admins, Enterprise Admins, Schema Admins) to
   **Deny log on locally**, **Deny log on through Remote Desktop Services**,
   **Deny log on as a batch job** and **Deny log on as a service**.
   **Deny access to this computer from the network** also stops network
   sign-ins, but it blocks remote administration of those computers with
   Tier Zero accounts as well.
4. Log off the account on the listed computers, or reboot them, to clear cached
   credentials. If any of them may have been compromised, change the account's
   password.
### Option B: Authentication Policy Silos
1. In **Active Directory Administrative Center > Authentication**, create an
   authentication policy and silo that allows Tier Zero accounts to authenticate
   only from Tier Zero computers (requires Windows Server 2012 R2+ domain functional level).
2. Assign the accounts and Tier Zero computers to the silo; test in audit mode first.
### Option C: Protected Users
Add the account to **Protected Users**: no NTLM, no delegation, no cached
credentials, 4-hour TGTs. Test first: it breaks NTLM-only apps for that account.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Where has the account logged on recently? (run on a computer from the finding)
Get-WinEvent -FilterHashtable @{ LogName = 'Security'; Id = 4624 } -MaxEvents 2000 |
    Where-Object { $_.Properties[5].Value -eq '<Account>' } |
    Select-Object TimeCreated, @{ n = 'LogonType'; e = { $_.Properties[8].Value } }

# Services and scheduled tasks running as the account on a computer
Get-CimInstance Win32_Service -ComputerName <Computer> | Where-Object StartName -like '*<Account>*'
Get-ScheduledTask -CimSession <Computer> | Where-Object { $_.Principal.UserId -like '*<Account>*' }

# Add the account to Protected Users (after testing)
Add-ADGroupMember -Identity "Protected Users" -Members "<Account>"
```

## Verify
After the deny rights apply (`gpupdate /force`, or the next refresh), a logon attempt
by the Tier Zero account on a listed computer must fail. Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
Remove the groups from the Deny user rights in the GPO (or unlink it) and run
`gpupdate /force`; remove the account from Protected Users with
`Remove-ADGroupMember "Protected Users" -Members "<Account>"`.
