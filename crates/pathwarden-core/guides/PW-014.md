# PW-014: krbtgt password not rotated

**Category:** Hygiene
**Typical owner:** AD / identity team

## What this finding means
The krbtgt account's password has not been changed within the configured period (180 days by
default). The key derived from this password signs and encrypts every Kerberos ticket-granting
ticket (TGT) in the domain.

## Why attackers care
Anyone who has ever obtained the krbtgt hash, for example through DCSync, a stolen DC backup or a
past breach, can forge TGTs for any user with any group membership. These are "golden tickets"
(Steal or Forge Kerberos Tickets: Golden Ticket, MITRE ATT&CK T1558.001). The forged tickets keep
working until the krbtgt password has been changed **twice**, because domain controllers accept
both the current and the previous key. Regular rotation limits how long a stolen key stays useful.

## Before you change anything
- Make sure Active Directory replication is healthy: `repadmin /replsummary` should show no
  failures. A rotation that does not reach every DC causes Kerberos failures.
- Read-only DCs have their own krbtgt_XXXXX accounts. Microsoft's script can handle those too.
- Rotate **twice**, with a wait between the rotations. The first change invalidates nothing on
  its own (the old key is still accepted as the previous key). The second change invalidates
  every ticket signed with the original key. Rotating twice in quick succession can break
  existing sessions and services before their tickets renew.
- Schedule the work in a change window and tell the service desk. Users may need to log off and on.

## Fix
### Option A: Microsoft's New-KrbtgtKeys.ps1 (recommended)
1. Download `New-KrbtgtKeys.ps1` from Microsoft's official GitHub repository (see References).
2. Run it on a domain-joined admin computer as a Domain Admin. Start with the **simulation** /
   read-only test modes it offers to check that all DCs are reachable and replicating.
3. Run the **reset** mode for the domain's krbtgt account (first rotation).
4. Wait at least the maximum user ticket lifetime (10 hours by default, see
   **Default Domain Policy > Kerberos Policy**) **and** until you confirm the change has replicated
   to every DC. Many organizations wait 24 hours.
5. Run the reset mode a second time (second rotation).
6. Repeat the double rotation at least every 180 days. After a suspected compromise, do it
   immediately.

### Option B: Manual reset
In **Active Directory Users and Computers**, enable **View > Advanced Features**, right-click
**krbtgt** in the Users container > **Reset Password** and enter any value. Windows replaces it
with a random password. Repeat after the wait described above. Prefer the script: it
verifies replication.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Check the current password age
Get-ADUser -Identity krbtgt -Properties PasswordLastSet | Select-Object Name, PasswordLastSet

# Confirm replication health before and between rotations
repadmin /replsummary

# Run Microsoft's script and follow its menu: simulation first, then reset.
# Run it twice in total, waiting >= max ticket lifetime (default 10h) and for full
# replication between the two resets.
.\New-KrbtgtKeys.ps1
```

## Verify
`Get-ADUser krbtgt -Properties PasswordLastSet` shows a recent date, and `repadmin /showobjmeta
<DC> "CN=krbtgt,CN=Users,DC=<domain>,DC=<tld>"` shows the same unicodePwd version on every DC.
Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
A krbtgt rotation cannot be undone. If clients report Kerberos errors after the first rotation,
wait for replication to finish and have affected users log off and on (or run `klist purge`).
Do not perform the second rotation until the first has fully replicated.
