# PW-017: AD CS ESC4: write access to a template from outside Tier Zero

**Category:** Attack path
**Typical owner:** PKI / AD CS administrators (AD team for delegated permissions)

## What this finding means
Accounts and groups outside Tier Zero can change the settings of a certificate template that a logon-trusted CA publishes, and can also enroll through that CA. The rights involved are Full Control, Write, Write DACL, Write Owner, ownership, or write access to the template's name and enrollment flags. Changing those settings turns an ordinary template into one that issues certificates for any identity.

## Why attackers care
This is ESC4 from SpecterOps' "Certified Pre-Owned". With write access, an attacker (tools such as Certipy have a one-command "make it vulnerable" option) flips the template to "supply in the request", removes manager approval, enrolls as a Domain Admin, and can even put the template back afterwards. Certificate templates live in the Configuration partition, so the permissions are easy to overlook in normal AD delegation reviews.

## Before you change anything
- Review the template's full permission list and who owns it:
  `dsacls "CN=<Template>,CN=Certificate Templates,CN=Public Key Services,CN=Services,CN=Configuration,DC=<domain>,DC=<tld>"`
- Find out why the account or group has write access: often a helpdesk or application team was given Full Control "to manage" a template, or a former PKI admin account still owns it.
- Keep Enroll / Autoenroll entries that are legitimately needed; only write rights are the problem.
- Record the current permissions (screenshot the Security tab, Advanced view) for rollback.

## Fix
### Option A: Remove the write permissions (recommended)
1. Open certtmpl.msc as an Enterprise Admin or the delegated PKI admin.
2. Right-click the template > Properties > **Security** tab > **Advanced**.
3. For each account or group named in the finding, remove the rights the finding lists: Full Control, Write, Modify permissions, Modify owner, and any entries granting "Write msPKI-Certificate-Name-Flag" or "Write msPKI-Enrollment-Flag". Keep Read and, if needed, Enroll.
4. On the same Advanced dialog, check the **Owner**. If it is not a PKI administrator group, change it to Enterprise Admins: the owner can always change the permissions.
5. If an entry is inherited, fix it on the Certificate Templates container (or the container above it it comes from) and check inheritance on the other templates.
6. Click OK.

Only the PKI administrators (by default Enterprise Admins and the forest root's Domain Admins) should be able to change certificate templates.

### Option B: Unpublish the template if it is unused
certsrv.msc > Certificate Templates > right-click the template > **Delete**. The template stops being issued; its permissions still need fixing before it is ever re-published.

### PowerShell / certutil
```powershell
# Show the template's permissions (adjust the configuration DN to your forest)
dsacls "CN=<Template>,CN=Certificate Templates,CN=Public Key Services,CN=Services,CN=Configuration,DC=<domain>,DC=<tld>"

# Show the flags an attacker would change, to compare with your baseline
certutil -dstemplate <Template> msPKI-Certificate-Name-Flag
certutil -dstemplate <Template> msPKI-Enrollment-Flag

# Unpublish the template from the CA (Option B)
certutil -config "<CAHost>\<CAName>" -SetCATemplates -<Template>
```

## Verify
- The Security tab shows write access only for Tier Zero (Enterprise Admins, Domain Admins of the root domain, SYSTEM) and the owner is a Tier Zero group.
- Compare the template flags with your recorded baseline to make sure nobody already modified the template.
- Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
Re-add the removed permissions from your recorded list via the Security tab, or re-publish the template with `certutil -config "<CAHost>\<CAName>" -SetCATemplates +<Template>`.
