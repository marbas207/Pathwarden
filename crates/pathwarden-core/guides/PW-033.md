# PW-033: Tier Zero account's password stored on computers outside Tier Zero

**Category:** Attack path
**Typical owner:** the server team that owns the computers, with the owner of the account

## What this finding means
A scheduled task or Windows service on a computer outside Tier Zero runs as a
Tier Zero account (a Domain Admin, a member of another Tier Zero group) and
stores that account's password on the computer. Windows keeps a task's password
in the computer's credential store and a service's in the LSA secrets; any
administrator of the computer (or anyone running as SYSTEM there) can recover it.
So every administrator of those computers controls the Tier Zero account.

There is one finding per account, listing every computer and task or service
that stores it. The evidence comes from two places, which give the same
finding: Pathwarden's built-in collector, which in a Full collection reads
the account each service runs as from the computers' registry (`ObjectName`)
and the account each scheduled task stores from its task file on `C$`
(run-as account and logon type only), both over Kerberos and never the password;
and TaskHound (an OpenGraph file, see `docs/opengraph.md`).

Tasks that store no password (S4U, interactive token) and services that run
as a group managed service account, a virtual account (`NT SERVICE\...`),
SYSTEM or a local account are not reported: there is no reusable domain
password to take. A disabled service or task still stores its password and
is reported. A Tier Zero computer that stores a Tier Zero password is in-tier: not
reported, though its path is kept.

Accounts outside Tier Zero whose password a computer stores are not findings,
but they are paths: if such an account controls Tier Zero, the path from the
computer's administrators shows up in PW-001 and the remediation path.

## Why attackers care
Stored credentials are one of the shortest routes from a member server to
the domain: local admin on one server, `mimikatz` or `secretsdump` for the
LSA secrets or the DPAPI-protected task credentials (T1555, Credentials from
Password Stores; T1003.004, LSA Secrets), and the attacker signs in as a
Domain Admin. Unlike a session, a stored password survives reboots and
sign-outs, and nobody has to be logged on.

## Before you change anything
- Open each listed task or service and confirm the account it runs as and
  its logon type (`Run whether user is logged on or not` with a stored
  password).
- Find out what the task or service really needs. A job that runs as a
  Domain Admin usually needs far less: rights on one share, one database,
  one OU.
- Export the task (`Export-ScheduledTask`) or note the service configuration
  so you can roll back.

## Fix
### Option A: Stop storing the password (recommended)
- Run the task or service as a **group managed service account** scoped to
  that computer, with only the rights it needs; or as SYSTEM, or a virtual
  account, if it needs no network identity of its own.
- If it truly needs Tier Zero rights, move it to a Tier Zero computer.
- **Then rotate the account's password**: every administrator of the computer
  could already have read it. For a Domain Admin, rotate twice if you also
  suspect Kerberos tickets were forged with it.

### Option B: Make the computer Tier Zero
Only if the computer really belongs there (a Tier Zero management server): add
it under Additional Tier Zero in Settings, then fix what PW-003 and PW-004
report about it.

### PowerShell
```powershell
# Tasks that store a password, on one computer
Get-ScheduledTask -CimSession "<Computer>" |
    Where-Object { $_.Principal.LogonType -eq 'Password' } |
    Select-Object TaskPath, TaskName, @{n='RunAs';e={$_.Principal.UserId}}

# Run the task as a gMSA (allowed to retrieve its password on <Computer>)
$p = New-ScheduledTaskPrincipal -UserId "<Domain>\<gMSA>$" -LogonType Password
Set-ScheduledTask -CimSession "<Computer>" -TaskPath "<TaskPath>" -TaskName "<TaskName>" -Principal $p

# Services that run as a domain account
Get-CimInstance Win32_Service -ComputerName "<Computer>" |
    Where-Object { $_.StartName -like '<Domain>\*' } | Select-Object Name, StartName

# Rotate the exposed account's password
Set-ADAccountPassword -Identity "<Account>" -Reset -NewPassword (Read-Host -AsSecureString "New password")
```

## Verify
For services and tasks found by the built-in collector, run a Full
collection again, then analyze it. For TaskHound's data, collect again with TaskHound **and its
coverage file** listing the computers you changed (`docs/opengraph.md`), then analyze
the new collection. Either way the finding is marked fixed
only when every computer that stored the password was read again in full, for
each kind that stored it there; a computer that wasn't reached, or whose services
or tasks were read only partly or not at all, keeps it open as "can't tell". A targeted retest can't check it: it
re-reads the directory, not the computers.

## Rollback
Re-import the exported task (`Register-ScheduledTask -Xml (Get-Content task.xml -Raw)`)
or restore the service account (`sc.exe config <Service> obj= <Account>`). Do
not restore a password that was exposed: set a new one.
