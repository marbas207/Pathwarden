# PW-007: Kerberos pre-authentication disabled (AS-REP roasting)

**Category:** Attack path or hygiene (hygiene when the account has no path to Tier Zero)
**Typical owner:** AD / identity team

## What this finding means
The account has "Do not require Kerberos preauthentication" set. Anyone who can
reach a domain controller can request an authentication response for it without
knowing its password, and part of that response is encrypted with the password.

## Why attackers care
AS-REP roasting (Steal or Forge Kerberos Tickets: AS-REP Roasting, T1558.004) does
not even need a domain account: an attacker on the network asks for the response and
cracks it offline. If the password is weak, they get the account; if the account is
privileged or has a path to Tier Zero, that is domain compromise.

## Before you change anything
- The flag is almost always a leftover from old Unix/Kerberos interop or a vendor
  install guide. Ask the account owner which system uses it.
- Check recent use: event 4768 on domain controllers with "Pre-Authentication Type"
  0 for this account shows clients authenticating without pre-auth.
- Very old MIT Kerberos or Java clients may fail once pre-auth is required; test with
  the owning application.

## Fix
### Option A: Require pre-authentication (recommended)
1. **Active Directory Users and Computers** > the account > **Properties > Account**.
2. Under **Account options**, clear **Do not require Kerberos preauthentication**.
3. **OK**, then test the application that uses the account.
### Option B: If an application genuinely needs it
Keep the flag only with a long random password (25+ characters), no privileged group
memberships, and monitoring of event 4768 for that account.

### PowerShell
```powershell
Import-Module ActiveDirectory

# All accounts with pre-authentication disabled
Get-ADUser -Filter { DoesNotRequirePreAuth -eq $true } -Properties DoesNotRequirePreAuth, Enabled

# Require pre-authentication again
Set-ADAccountControl -Identity "<Account>" -DoesNotRequirePreAuth $false

# Option B: set a long random password if the flag must stay
Set-ADAccountPassword -Identity "<Account>" -Reset -NewPassword (Read-Host -AsSecureString "New password")
```

## Verify
`Get-ADUser "<Account>" -Properties DoesNotRequirePreAuth` must show `False`. Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
`Set-ADAccountControl -Identity "<Account>" -DoesNotRequirePreAuth $true` restores the
previous behavior if an application breaks; then plan Option B for that account.
