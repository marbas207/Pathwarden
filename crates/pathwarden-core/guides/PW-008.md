# PW-008: Tier Zero accounts without delegation protection

**Category:** Hygiene
**Typical owner:** AD / identity team

## What this finding means
These Tier Zero user accounts are neither members of the Protected Users group nor marked
"Account is sensitive and cannot be delegated". Their credentials can therefore be cached on the
computers they log on to, and any service trusted for delegation can forward their Kerberos
tickets.

## Why attackers care
An attacker who controls a server trusted for unconstrained or constrained delegation can
impersonate any delegatable account that authenticates to it, including Domain Admins
(Kerberos delegation abuse, MITRE ATT&CK T1558). Accounts outside Protected Users also leave
NTLM hashes and long-lived credentials in LSASS memory, which tools like Mimikatz extract
(OS Credential Dumping, T1003.001). Protected Users removes both of these options for its members.

## Before you change anything
- Protected Users members **cannot** use NTLM, DES or RC4 Kerberos encryption, Kerberos
  delegation, or cached (offline) logons, and their Kerberos TGTs last 4 hours. Anything
  that relies on these will break for the account.
- Never add service accounts or computer accounts to Protected Users. Use the
  "sensitive and cannot be delegated" flag (Option B) for service accounts that are Tier Zero.
- Check for NTLM use by the account first: enable NTLM auditing
  ("Network security: Restrict NTLM: Audit NTLM authentication in this domain") and review
  event 8004 on domain controllers, or 4624 events with Authentication Package NTLM.
- Make sure the domain functional level is Windows Server 2012 R2 or later. Protected Users
  only takes full effect from that level.
- Keep at least one break-glass account **outside** Protected Users in case Kerberos fails.
  Store its password offline.

## Fix
### Option A: Add Tier Zero user accounts to Protected Users (recommended)
1. Open **Active Directory Users and Computers** (dsa.msc).
2. Go to the **Users** container and open the **Protected Users** group.
3. **Members** tab > **Add**. Add one test admin account first.
4. Sign out and sign back in with that account. Confirm your admin tools still work.
5. Add the remaining interactive Tier Zero admin accounts listed in the finding.

### Option B: Mark the account "sensitive and cannot be delegated"
Use this for accounts that cannot join Protected Users, such as Tier Zero service accounts.
1. In dsa.msc, open the account > **Account** tab.
2. Under **Account options**, tick **Account is sensitive and cannot be delegated**.
3. Click **OK**.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Option A: add an interactive admin account to Protected Users
Add-ADGroupMember -Identity "Protected Users" -Members "<Account>"

# Option B: block delegation for an account that cannot join Protected Users
Set-ADUser -Identity "<Account>" -AccountNotDelegated $true
```

## Verify
```powershell
# Members of Protected Users
Get-ADGroupMember -Identity "Protected Users" | Select-Object SamAccountName

# Accounts flagged as not delegatable
Get-ADUser -Identity "<Account>" -Properties AccountNotDelegated |
    Select-Object SamAccountName, AccountNotDelegated
```
Collect again (or use Retest on the finding) and confirm the finding ID is gone (or lists fewer accounts).

## Rollback
- Remove the account from the group: `Remove-ADGroupMember -Identity "Protected Users" -Members "<Account>"`.
  The change applies at the account's next logon. Existing tickets expire within 4 hours.
- Clear the flag: `Set-ADUser -Identity "<Account>" -AccountNotDelegated $false`.
