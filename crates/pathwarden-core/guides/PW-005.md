# PW-005: Unconstrained delegation outside domain controllers

**Category:** Attack path
**Typical owner:** AD / identity team with the server or application owner

## What this finding means
A computer or user that is not a domain controller is "trusted for delegation to
any service" (unconstrained delegation). Every account that authenticates to it
with Kerberos leaves a forwardable ticket (TGT) in its memory. That makes the computer
as sensitive as a domain controller.

## Why attackers care
An attacker with admin rights on the computer coerces a domain controller to
authenticate to it (PrinterBug / MS-RPRN, PetitPotam / MS-EFSR), captures the DC's
TGT from memory and uses it to DCSync the domain (Steal or Forge Kerberos Tickets,
T1558). No credentials of the victim DC are needed; only control of this computer.

## Before you change anything
- Ask the application owner why delegation was enabled. Common legacy reasons: IIS
  or SQL Server front ends that access back-end services as the user.
- Identify which back-end services the computer must delegate to (SPNs). Kerberos
  service ticket events 4769 on domain controllers with this computer as the requesting
  service show what it actually requests.
- Constrained or resource-based constrained delegation (RBCD) supports nearly all
  such scenarios; plan the replacement before removing the flag.

## Fix
### Option A: Switch to constrained delegation (recommended)
1. **Active Directory Users and Computers** > the computer (or service account) >
   **Properties > Delegation**.
2. Select **Trust this computer for delegation to specified services only**, then
   **Use Kerberos only** where possible.
3. **Add** only the back-end services (SPNs) the application needs, **OK**.
### Option B: Remove delegation entirely
If nothing needs it, select **Do not trust this computer for delegation**.
### Option C: Resource-based constrained delegation
Configure delegation on the back-end resource instead (its
`PrincipalsAllowedToDelegateToAccount`), which keeps control with the resource owner.

Until unconstrained delegation is removed, treat the computer as Tier Zero, with the
same administrative controls and monitoring as domain controllers. Turn off the Print
Spooler on domain controllers where you can, against coercion through the print service
(PrinterBug). Keep domain controllers up to date against other coercion such as PetitPotam.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Find all non-DC accounts with unconstrained delegation
Get-ADComputer -Filter { TrustedForDelegation -eq $true -and PrimaryGroupID -ne 516 -and PrimaryGroupID -ne 521 } -Properties TrustedForDelegation
Get-ADUser -Filter { TrustedForDelegation -eq $true } -Properties TrustedForDelegation

# Remove unconstrained delegation from one computer
Set-ADAccountControl -Identity "<Computer>$" -TrustedForDelegation $false

# Optional: constrained delegation to a specific back-end service
Set-ADComputer -Identity "<Computer>" -Add @{ 'msDS-AllowedToDelegateTo' = 'MSSQLSvc/<backend>.<domain>:1433' }

# Resource-based alternative, set on the back-end computer
Set-ADComputer -Identity "<BackendComputer>" -PrincipalsAllowedToDelegateToAccount (Get-ADComputer "<Computer>")
```

## Verify
`Get-ADComputer "<Computer>" -Properties TrustedForDelegation` must show `False`.
Test the application end to end as a normal user. Collect again (or use Retest on the finding) and confirm the finding ID is gone.

## Rollback
`Set-ADAccountControl -Identity "<Computer>$" -TrustedForDelegation $true` restores
the previous setting. Clear any added constrained delegation with
`Set-ADComputer "<Computer>" -Clear msDS-AllowedToDelegateTo`.
