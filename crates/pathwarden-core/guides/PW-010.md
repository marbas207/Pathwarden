# PW-010: Old Tier Zero passwords

**Category:** Hygiene
**Typical owner:** AD / identity team (service account owners for service accounts)

## What this finding means
These Tier Zero accounts have passwords older than the configured limit (365 days by default).
The longer a privileged password lives, the more places it may have leaked to: old backups,
scripts, memory dumps, password managers of former staff, or earlier breaches.

## Why attackers care
Attackers routinely recover old credential material, such as NTDS.dit backups, LSASS dumps from
decommissioned servers and cracked hashes from earlier intrusions. A password that has not changed
since then still works (Valid Accounts: Domain Accounts, MITRE ATT&CK T1078.002). If an attacker
has the NTLM hash of an unchanged account, pass-the-hash keeps working until the password changes
(Use Alternate Authentication Material: Pass the Hash, T1550.002).

## Before you change anything
- For **service accounts**, find every place the password is configured (services, scheduled
  tasks, IIS application pools, application config files, scripts) before rotating. Check
  4625 failures on domain controllers right after the change to catch anything you missed.
- Check for "password never expires": `Get-ADUser <Account> -Properties PasswordNeverExpires`.
- Interactive admins should change their own password so they choose and store it securely.
- Prefer migrating service accounts to group Managed Service Accounts (gMSA), which rotate
  automatically.

## Fix
### Option A: Rotate the password now (recommended)
1. Open **Active Directory Users and Computers** (dsa.msc).
2. Right-click the account > **Reset Password**.
3. Set a long random password (25+ characters for service accounts) and store it in your
   privileged access vault.
4. For service accounts, update every place that uses the password, then restart the dependent
   services.

### Option B: Move service accounts to a gMSA
1. Create a gMSA (`New-ADServiceAccount`) that the computers running the service are allowed to use.
2. Install it on those computers (`Install-ADServiceAccount`) and reconfigure the service to run as
   `<Domain>\<gMSA>$` with an empty password.
3. Disable the old account once the service runs under the gMSA.

### PowerShell
```powershell
Import-Module ActiveDirectory

# Review password age
Get-ADUser -Identity "<Account>" -Properties PasswordLastSet, PasswordNeverExpires |
    Select-Object SamAccountName, PasswordLastSet, PasswordNeverExpires

# Reset the password (prompts for the new value without echoing it)
Set-ADAccountPassword -Identity "<Account>" -Reset -NewPassword (Read-Host -AsSecureString "New password")

# Optional: let the normal password policy apply again
Set-ADUser -Identity "<Account>" -PasswordNeverExpires $false
```

## Verify
```powershell
Get-ADUser -Identity "<Account>" -Properties PasswordLastSet |
    Select-Object SamAccountName, PasswordLastSet
```
Collect again (or use Retest on the finding) and confirm the finding ID is gone (or lists fewer accounts).

## Rollback
A password cannot be "un-rotated". If a service breaks, set the new password wherever the
service is configured (or reset again to a value you control and update the service), then
restart the service. Check 4625 events to find the failing computer.
