# PW-019: AD CS ESC8: NTLM relay to web enrollment

**Category:** Attack path
**Typical owner:** PKI / AD CS administrators (web server / IIS administrators)

## What this finding means
The CA offers web-based enrollment (Certificate Authority Web Enrollment at /certsrv, or the Certificate Enrollment Web Service) over HTTP, or over HTTPS without Extended Protection for Authentication (EPA). Those endpoints accept NTLM authentication, so a relayed NTLM logon from another computer is accepted as if that computer had asked for a certificate.

## Why attackers care
This is ESC8 from SpecterOps' "Certified Pre-Owned". An attacker on the network coerces a domain controller into authenticating to a computer they control (for example with PetitPotam or the printer bug), relays that NTLM authentication to the CA's web enrollment page with tools such as ntlmrelayx or Certipy, and receives a certificate for the domain controller's computer account. With it they obtain the DC's credentials and can DCSync the domain. The attacker needs no privileges beyond network access, which is why Pathwarden treats this as exposed to every account.

## Before you change anything
- List the endpoints reported in the finding and check who uses them. Most organizations no longer use the /certsrv pages; autoenrollment and certreq talk to the CA over RPC/DCOM and are unaffected by the changes below.
- If the Certificate Enrollment Web Service is used (for example by non-domain or cross-forest clients), plan HTTPS with EPA rather than removal.
- Check IIS on the CA server: Sites > Default Web Site > CertSrv (and any *_CES_* applications), and its bindings.

## Fix
### Option A: Remove web enrollment if it is not used (recommended)
1. On the CA server, uninstall the role services with the commands below (Web Enrollment, and the Enrollment Web Service if present and unused).
2. Remove the now-unused IIS site bindings if nothing else on the server needs them.

### Option B: Require HTTPS with Extended Protection (when web enrollment is needed)
1. IIS Manager > Sites > Default Web Site > **CertSrv** > SSL Settings: tick **Require SSL**.
2. CertSrv > **Authentication** > Windows Authentication > Advanced Settings: set Extended Protection to **Required**.
3. Repeat for each Certificate Enrollment Web Service application (named <CAName>_CES_Kerberos or similar).
4. Remove the HTTP (port 80) binding from the site if nothing else needs it.
5. Run `iisreset` and test enrollment from a client.

### Option C: Block NTLM to the CA server
Disable NTLM for incoming traffic on the CA server (Group Policy: Network security: Restrict NTLM: Incoming NTLM traffic = Deny all accounts), after auditing with the corresponding audit setting. This also blocks the relay.

### PowerShell / certutil
```powershell
# Option A: remove the Web Enrollment role service (run on the CA server)
Uninstall-AdcsWebEnrollment -Force
Uninstall-WindowsFeature ADCS-Web-Enrollment

# Option A: remove the Certificate Enrollment Web Service if present and unused
Uninstall-AdcsEnrollmentWebService -Force
Uninstall-WindowsFeature ADCS-Enroll-Web-Svc

# Option B: require Extended Protection on CertSrv (verify in IIS Manager afterwards)
& "$env:windir\system32\inetsrv\appcmd.exe" set config "Default Web Site/CertSrv" -section:system.webServer/security/authentication/windowsAuthentication /extendedProtection.tokenChecking:"Require" /commit:apphost
```

## Verify
- Browsing to `http://<CAHost>/certsrv/` fails (removed, or redirected/blocked), and HTTPS requires EPA (IIS Manager shows Extended Protection: Required).
- Collect again (or use Retest on the finding) and confirm the finding ID is gone. Endpoint data comes from the collector probing the CA (SharpHound and RustHound-CE both do this).

## Rollback
Reinstall with `Install-WindowsFeature ADCS-Web-Enrollment` followed by `Install-AdcsWebEnrollment`, or set Extended Protection back to Off/Accept and re-add the HTTP binding in IIS Manager.
