# PW-011: Computers without LAPS

**Category:** Hygiene
**Typical owner:** Desktop / server team, with the AD team for schema and permissions

## What this finding means
These enabled computers (domain controllers excluded) do not have their local administrator
password managed by LAPS. Their built-in local Administrator password is probably set by an
image or a script, and is often identical across many computers.

Standalone managed service accounts (sMSA) are not reported: they appear as computer-like
objects but have no interactive local administrator, so LAPS doesn't apply. Pathwarden
recognizes them from SharpHound's `msa` flag, and in RustHound-CE or built-in collections
(which type an sMSA as a computer with no flag) from its membership of the domain's Managed
Service Accounts container.

## Why attackers care
After compromising one computer, an attacker dumps the local Administrator hash from the SAM and
tries it everywhere. If the password is shared, every computer with the same password falls
(Use Alternate Authentication Material: Pass the Hash, MITRE ATT&CK T1550.002, and Lateral
Movement via SMB/Windows Admin Shares, T1021.002). This is one of the most common ways a single
phished workstation turns into domain-wide compromise during a pentest.

## Before you change anything
- Windows LAPS is built into Windows 10/11 and Windows Server 2019 and later with the April 2023
  update. Older systems need legacy Microsoft LAPS, or an upgrade.
- Decide who may read passwords. By default only Domain Admins can. Grant read access to a
  dedicated helpdesk/desktop group per OU, never to broad groups.
- Check for tooling that relies on the shared local admin password (deployment scripts, remote
  support tools) and move it to LAPS retrieval or domain accounts first.
- The schema update is forest-wide and needs Schema Admins rights. Plan it with the AD team.

## Fix
### Option A: Deploy Windows LAPS by Group Policy (recommended)
1. Extend the schema once: run `Update-LapsADSchema` as a Schema Admin.
2. Let computers write their own password: `Set-LapsADComputerSelfPermission -Identity "<OU>"`.
3. Grant read access to the support group: `Set-LapsADReadPasswordPermission -Identity "<OU>" -AllowedPrincipals "<Domain>\<SupportGroup>"`.
4. In **Group Policy Management**, create a GPO linked to the OU and open
   **Computer Configuration > Policies > Administrative Templates > System > LAPS**.
5. Enable **Configure password backup directory** = **Active Directory**, and set
   **Password Settings** (complexity, length 15+, age 30 days).
6. Run `gpupdate /force` on a test computer and check that a password appears (see Verify).
7. Widen the GPO to the remaining OUs in the finding.

### Option B: Intune (for Entra-joined or co-managed devices)
Use an Intune **Endpoint security > Account protection > Local admin password solution**
policy with the backup directory set to Active Directory (for hybrid-joined) or Entra ID.

### PowerShell
```powershell
# One-time forest preparation (Schema Admins)
Update-LapsADSchema

# Per OU: allow computers to update their own password attributes
Set-LapsADComputerSelfPermission -Identity "<OU>"

# Per OU: allow the support group to read passwords
Set-LapsADReadPasswordPermission -Identity "<OU>" -AllowedPrincipals "<Domain>\<SupportGroup>"

# After GPO deployment: confirm a computer has a managed password
Get-LapsADPassword -Identity "<Computer>" -AsPlainText
```

## Verify
`Get-LapsADPassword -Identity "<Computer>"` returns a password and an expiration time. On the
client, the event log **Applications and Services Logs > Microsoft > Windows > LAPS > Operational**
shows successful password updates. Collect again (or use Retest on the finding) and confirm the finding ID is gone (or lists
fewer computers).

## Rollback
Unlink or disable the LAPS GPO. Computers keep their last LAPS-set password, so retrieve it with
`Get-LapsADPassword` before removing read permissions. The schema extension is permanent but
harmless.
